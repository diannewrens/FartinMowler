Agent memory and the smell of haunted context

The industry has rediscovered memory, which is adorable because computers have been remembering things for a while. The new pitch is more personal. The assistant should remember your preferences, your projects, your tone, your stack, your allergies to YAML, and the exact shape of the little scream you make when someone says "quick sync".

Some of this is good. Repeating the same context to every agent is a tax. A coding assistant that remembers repo conventions can avoid wasting your morning. A support assistant that remembers the customer's plan tier can stop asking haunted onboarding questions.

Persistent memory is useful until it becomes a ghost pantry: full of old snacks, mislabeled jars, and one belief from March that now runs billing.

Short version

  • Agent memory is not a magic brain. It is application state with extra confidence.
  • The smell starts when remembered hints become hidden policy.
  • Every durable memory needs scope, source, owner, expiry, and a way to challenge it.
  • Separate preferences, facts, decisions, credentials, and learned procedures. They do not rot at the same speed.
  • If users cannot see and edit what the agent remembers, the product is not personalized. It is haunted.

The smell

The haunted context smell appears when an agent carries durable memory across tasks without treating that memory like a real dependency. It remembers that the team "usually deploys on Fridays". It remembers that Alice "prefers concise reviews". It remembers that an old migration plan said PostgreSQL 14, so it keeps suggesting PostgreSQL 14 six months after the platform team moved on.

At first, the memory feels charming. The assistant stops asking what test command to run. It knows the house style. It calls the internal package registry by the right name. Then one day it rejects a pull request because it "remembers" a rule nobody wrote down, or routes a customer issue to the wrong queue because a stale note survived a reorg. The ghost has joined standup.

The danger is not only privacy, although privacy is sitting in the corner with a clipboard and a headache. The architectural problem is hidden state. A prompt plus a model plus a tool call is already enough moving parts. Add invisible memory, and now the same request can behave differently depending on what the system believes it learned last week. Reproducibility leaves quietly through the side door.

Humans do this too, of course. We remember nonsense constantly. The difference is that humans can be asked, "Why did you think that?" A lot of agent memory systems answer with a shrug wearing JSON.

Why it happens

Teams add memory because context windows are expensive, users hate repetition, and demos look better when the assistant says, "I remember you prefer TypeScript." Product managers see retention. Engineers see fewer setup prompts. Executives see a slide that says personalization and briefly forget databases exist.

The simplest implementation is a bucket of notes. Save extracted facts. Retrieve similar facts later. Inject them into the prompt. This works well enough to be dangerous. Similarity search does not know whether a memory is still true. It does not know whether the source was a user preference, an inferred guess, a failed experiment, or a joke in a Slack thread that should have died there with the other raccoons.

Memory also collapses categories that should stay separate. A preference is not a fact. A fact is not a policy. A policy is not a credential. A temporary workaround is not an architectural principle, even if someone wrote it in a very authoritative sentence during an outage. When these all become "context", the agent starts cooking with everything in the fridge, including the receipt.

Then there is the incentive problem. A memory system that says less looks less magical. So products remember aggressively. They infer from behavior. They keep notes forever because deletion is hard and future usefulness is easy to imagine. The result is context compost. Rich, dark, full of nutrients, and maybe not what you want near the drinking water.

The pattern

Treat memory as a typed, inspectable store, not a vibes drawer. The agent may remember things, but each memory should carry its shape: what kind of thing it is, where it came from, when it was last confirmed, who can edit it, when it expires, and which actions are allowed to use it.

Start with a small taxonomy. Preferences cover tone, formatting, interface choices, and other low-risk defaults. Project facts cover repo commands, service names, branch rules, and environment constraints. Decisions cover approved architecture choices and should link to records, tickets, or docs. Procedures cover repeatable workflows and need tests or examples. Secrets should not be memories. Secrets belong in secret stores, where they can live their miserable little lives under adult supervision.

Make retrieval explainable. When the agent uses a memory, show it in the run log or UI: "Used memory: this repo runs pnpm test, confirmed May 12 by package.json." That is much better than a confident answer with mystery seasoning. If the memory affects a state-changing action, require a stronger source than an inferred note. Old vibes should not approve invoices.

Give memories expiry. Some should last until the user changes them. Some should expire after a sprint. Some should be revalidated when the repo changes, when a dependency file moves, when a team changes ownership, or when a human disputes the result. Forgetting is not failure. Forgetting is garbage collection with manners.

Build a correction path. Users should be able to list, edit, pin, archive, and delete memories. Developers should be able to reproduce a run with a memory snapshot. Reviewers should be able to see whether the agent followed written policy or a stale little whisper from the past.

The fart test

  • Can a user see the exact memories that influenced an answer or action?
  • Does every memory have a type, source, timestamp, owner, and expiry rule?
  • Are inferred memories kept out of high-risk actions unless confirmed?
  • Can you replay an agent run with the same memory snapshot?
  • Is there a boring delete button, or does forgetting require archaeology?

If the answers are mostly no, you do not have agent memory. You have a rumor cache with a user interface. It will feel smart right up until it remembers the wrong thing with perfect posture.

Let agents remember. Just make them remember like software, not like a haunted Victorian child whispering deployment advice through the walls. Memory is state. State needs shape. Otherwise the past keeps farting into production and everyone pretends it is personalization.
