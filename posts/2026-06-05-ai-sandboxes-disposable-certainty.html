AI sandboxes and the smell of disposable certainty

AI coding agents love a sandbox. Give the agent a fresh checkout, a temporary filesystem, a browser preview, a package cache, maybe a little terminal with training wheels, and suddenly the whole thing feels civilized. The agent can make a mess somewhere nobody has to smell it until the diff comes home.

That is progress. A disposable environment is better than letting an eager robot rummage around a developer laptop full of SSH keys, stale branches, pet aliases, and one shell function named deploy_real that nobody should touch without a priest. Isolation matters.

The smell starts when the sandbox becomes proof. The agent says the app ran. The preview loaded. The tests passed in the clean little room. Everyone relaxes. Then production rejects the patch because the clean little room did not have the same secrets, feature flags, data shape, native dependencies, DNS behavior, queue backlog, auth provider, or deeply cursed build cache as the place where the software actually lives.

A sandbox is a rehearsal room. It is not the building inspector.

Short version

  • AI sandboxes are useful because they limit blast radius and make agent work reviewable.
  • They get smelly when a disposable environment starts passing for production evidence.
  • The hard parts are parity, secrets, state, network policy, provenance, and cleanup.
  • If the sandbox cannot explain what it did and what it could not reproduce, it is a very tidy liar.

The smell

The demo is clean. The agent opens a task, clones the repo, edits the code, runs the test suite, starts the dev server, captures a screenshot, and produces a pull request with the emotional range of a project manager who just discovered bullet points. The environment disappears afterward. No polluted laptop. No accidental credential leak. No twelve-minute argument about whose node version is haunted.

Then the false comfort creeps in. The sandbox passed, so the change must be safe. The preview rendered, so the UX must work. The agent tested the happy path, so the integration must be fine. This is disposable certainty: confidence manufactured by an environment designed to forget things.

You can smell it in the review comments. "Works in the agent sandbox." "Preview looks good." "All checks passed locally." These sentences are not useless, but they are not final evidence. They tell you the patch survived one small habitat. They do not tell you whether it can survive the swamp where customers, cron jobs, OAuth callbacks, old data, and angry caches gather to exchange spores.

The worst version hides behind ephemerality. Because the environment is temporary, nobody keeps enough receipts. The package install logs vanish. The agent's browser state vanishes. The exact command order vanishes. The network denies one request, retries another, and the trace goes wherever abandoned sandboxes go to die. The team gets a diff and a vibe. Very modern. Also slightly damp.

Why it happens

Sandboxes solve one real problem so neatly that they tempt teams to pretend they solved several adjacent problems too. They isolate tools. They constrain credentials. They make experiments cheap. They give reviewers a place to reproduce agent behavior without inviting the agent into the family silver drawer. All excellent.

But isolation cuts both ways. The safer the room, the less it resembles production. Real systems depend on awkward state: old migrations, weird tenants, expired tokens, regional settings, retained browser cookies, billing plans created before the current pricing model, and a feature flag spreadsheet that should have been a database in 2021. A sterile checkout cannot reveal problems caused by dirty history unless you deliberately bring some dirt.

Secrets are another trap. The sandbox usually gets fake credentials or narrowly scoped tokens, which is correct. Then the agent cannot exercise the real payment provider, email service, warehouse export, SSO flow, or deployment path. It stubs the edge and reports success near the edge. That is still useful if the report says "stubbed here." It is poisonous if the report says "verified" and everyone nods because the screenshot has a green button.

Network policy gets weird too. Some sandboxes cannot reach the private service. Some can reach too much. Some have package managers pointed at public registries but not internal mirrors. Some allow outbound calls during tests that production blocks. The agent experiences these as ordinary tool errors and may patch around them. Congratulations, your architecture now includes a model adapting to a fake network topology. The smell is faintly electrical.

Finally, cleanup is easy to confuse with accountability. Destroying the environment removes the mess, but it can also remove the evidence. If the sandbox is gone before the reviewer can see the commands, logs, file mutations, generated artifacts, and failed attempts, the review has to trust the agent's summary. Trusting a generated summary of a vanished environment is how adults accidentally reinvent folklore.

The pattern

Treat the sandbox as a bounded evidence generator. Its job is not to prove the system is correct. Its job is to produce a clear record of what was tried, what passed, what failed, what was mocked, and what could not be checked. That record should travel with the pull request like a slightly boring customs form.

Start with sandbox tiers. A scratch tier is for exploration and destructive experiments. A review tier runs the normal local suite, lints, build checks, and preview smoke tests. A parity tier is closer to production: seeded data, internal package mirrors, feature flags, policy-controlled network access, and enough secrets to test integrations without giving the agent a flamethrower.

Make gaps visible. If the payment API was mocked, say so. If the SSO callback could not run, say so. If the preview used seed data instead of tenant data, say so. A sandbox report should include negative evidence: "not tested against production-like billing plans" is more useful than a heroic paragraph about comprehensive validation. The latter smells like someone sprayed cologne on a failing smoke test.

Keep receipts after teardown. Preserve the command transcript, tool calls, environment image, dependency lockfile, test results, screenshots, browser console errors, and any generated files the agent chose not to commit. You do not need a forensic museum for every typo fix, but the reviewer should be able to answer a basic question: what happened in the room before the room was deleted?

Use capability-scoped credentials rather than all-or-nothing fake worlds. The agent should get tokens that can read a test tenant, write to a disposable namespace, call a staging endpoint, or trigger a dry-run deployment. The scope should be visible in the report. "Ran with staging.read_orders and test_email.send" is a lot better than "used credentials," which is the architectural equivalent of coughing into your sleeve.

Then connect sandbox results to release gates. A green sandbox can open a review. It should not automatically bless a risky merge unless the risky parts were actually exercised. If the change touches auth, billing, data migration, permissions, or customer-visible commitments, require the parity tier or a human-owned follow-up check. The sandbox can hold the flashlight. It should not sign the occupancy permit.

The Fart Test

  • Can you name which sandbox tier produced the evidence for this change?
  • Does the report say what was mocked, skipped, blocked, or impossible to reproduce?
  • Are command logs, test results, screenshots, and tool calls preserved after teardown?
  • Do sandbox credentials have visible, narrow capabilities instead of magic access or useless fakes?
  • Would the same patch face stronger gates if it touched auth, billing, migrations, permissions, or production data?

Disposable environments are good. Disposable evidence is not. Let the agent make a mess in a clean room, but keep the receipts, label the fake furniture, and do not confuse a tidy rehearsal with a certificate from the Ministry of Not Farting Up Production.
