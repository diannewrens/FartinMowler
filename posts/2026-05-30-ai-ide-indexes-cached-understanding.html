AI IDE indexes and the smell of cached understanding

The modern AI IDE wants to know your repository. Not just open files. Not just symbols. The whole thing: imports, tests, docs, recent commits, embeddings, dependency graphs, blame hints, style rules, and the little fossil layer of comments that says "temporary" from three reorgs ago.

This is useful. A coding assistant that can see the shape of the codebase is better than one guessing from the current tab like a raccoon reading a restaurant menu through a window. The smell starts when the IDE's index becomes a private architecture model that nobody audits, refreshes, scopes, or treats as fallible. Then the assistant is not pairing with your code. It is pairing with yesterday's rumor about your code.

A repo index is a map. If the map updates slower than the territory, do not let it drive the excavator.

Short version

  • AI IDE indexes are valuable when they help assistants find relevant files, APIs, tests, and conventions.
  • They get smelly when stale embeddings or symbol maps start passing for current architectural knowledge.
  • The fix is boring: freshness signals, source citations, scoped retrieval, invalidation rules, and tests that catch wrong assumptions.
  • If the assistant cannot tell you which version of the repo it thinks it understands, it does not understand the repo. It has vibes with a cache directory.

The smell

The first symptom is confidence. The assistant proposes a change across six files and explains that it follows the existing pattern. It names the service layer. It references the old validator. It imports a helper with the kind of calm authority usually reserved for people who have never run the test suite.

Then you look closer. The helper was deleted last week. The validator moved behind a feature flag. The "existing pattern" came from a migration shim that should not be copied into new code. The generated patch compiles after two small fixes, which makes the whole thing more dangerous. Wrong code that obviously explodes is a gift. Wrong code that smells faintly like the codebase is how teams adopt ghosts.

This is cached understanding. The IDE has an index. The agent has snippets. The prompt has retrieved examples. Together they produce the emotional texture of expertise. But architecture is not texture. Architecture is the current set of boundaries, contracts, failure modes, ownership rules, and tradeoffs that make the software behave under pressure. Some of that is in code. Some of it is in tests. Some of it is in docs. Some of it is in the scar tissue nobody indexed because it lives in incident reviews and the face your platform lead makes when someone says "just add a wrapper."

Why it happens

Code search used to be humble. You asked for a symbol, got a list of files, and decided what mattered. AI IDEs add a middle layer that decides relevance before you see it. That layer may combine lexical search, embeddings, language server data, dependency graphs, open buffers, recent edits, and whatever proprietary spice the vendor sprinkled into the stew. The result feels like context, but it is really a ranking system wearing a cardigan.

Ranking systems age. A branch changes. Generated files appear. A package boundary moves. A migration removes the path the assistant learned from. A mono repo holds five applications with similar names and different rules. The index may refresh eventually, but "eventually" is not an architectural guarantee. If the assistant retrieves an old implementation because it has high semantic similarity, it can reproduce the exact pattern the team just escaped. Congratulations, you have invented regression with good posture.

There is a second problem: missing negative knowledge. Indexes are good at finding examples of what exists. They are worse at knowing what must not be copied. The codebase often contains deprecated APIs, compatibility adapters, old auth flows, temporary forks, flaky tests, generated clients, and vendor patches. Humans learn to treat these areas like suspicious leftovers in the back of the fridge. An assistant sees examples. The smell becomes strongest when the repo contains both the desired pattern and the old forbidden one, and the old one has better names.

Generated code makes it worse. AI tools create more files, more near duplicates, more local conventions, and more helper abstractions that look intentional because they are formatted. The next assistant indexes that output and treats it as precedent. Now the system has a memory of its own droppings. This is not always bad. Sometimes generated scaffolding becomes real architecture. But it needs promotion, review, and ownership, not automatic canonization by an embedding job with no shame gland.

The pattern

Treat the IDE index as an evidence source, not an oracle. Every retrieved file should carry provenance: path, commit or timestamp, branch, whether it is generated, whether it is deprecated, and why it was selected. If the assistant cites a pattern, it should point to the files and tests that define that pattern. "This matches the existing style" is not enough. Existing where? Current as of when? Owned by whom? Blessed by what test?

Add freshness to the workflow. The assistant should know when the index is stale relative to the working tree. If files changed, dependencies updated, or the branch diverged, retrieval needs to say so. For risky edits, force a refresh or fall back to direct file reads. This sounds annoying until you compare it with reviewing a beautiful patch built on a deleted abstraction. A little friction at selection time beats a large fart at merge time.

Mark dangerous examples. Deprecated directories, generated clients, compatibility layers, fixtures, experiments, and old migrations need machine readable labels. A human warning in a README may help a human. It will not reliably stop a retrieval system from grabbing the wrong thing. Put the warning where the tool can consume it: metadata files, lint rules, codeowners, path policies, or explicit retrieval exclusions. If an assistant can read your entire repo but cannot tell the difference between a pattern and a museum exhibit, narrow its diet.

Keep architecture decisions outside the index fog. Short ADRs, boundary docs, package rules, and test names give the assistant better handles than folklore. Do not write essays for the machine. Write small, specific constraints humans also want: "new billing writes go through BillingCommandGateway," "do not import legacy-auth in new code," "orders owns refund state," "generated clients are not style examples." The goal is not more documentation perfume. The goal is fewer plausible lies.

Finally, review generated changes for assumption drift. Ask what the patch believed about the system. Which API did it think was current? Which directory did it treat as canonical? Which tests did it assume covered the behavior? This moves review from line polishing to model checking, in the plain old engineering sense. You are not grading the assistant's prose. You are checking the map against the territory before someone pours concrete.

The Fart Test

  • Can the assistant show the exact files, commits, and tests behind the pattern it claims to follow?
  • Does the index know which paths are deprecated, generated, experimental, or forbidden as examples?
  • Will retrieval warn when the working tree or branch is newer than the index?
  • Can reviewers see the assumptions behind a generated patch, not just the diff?
  • If an old implementation has better names than the new one, will the assistant still choose correctly?

AI IDE indexes are worth having. They make assistants less blind, which is polite. But cached understanding is still cached. Refresh the map, label the swamp, and do not let yesterday's architecture toot confidently into tomorrow's pull request.
