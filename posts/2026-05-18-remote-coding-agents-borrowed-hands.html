Remote coding agents and the smell of borrowed hands

The new fashion is to hand a ticket to a remote coding agent and receive a branch later, like dry cleaning with unit tests. The appeal is obvious. Backlogs are long, engineers are tired, and half the work in a codebase looks small until someone opens the closet and finds twelve years of adapter classes wearing each other's coats.

There is nothing foolish about delegation. A service that can clone a repository, inspect an issue, edit files in a sandbox, run tests, and propose a change is a useful tool. It can remove drudgery. It can draft migrations. It can chase simple bugs while humans argue about names, which remains our oldest distributed system.

A remote coding agent is not a junior developer. It is a borrowed pair of hands attached to a very confident filing cabinet.

Short version

  • Remote coding agents work best on bounded changes with crisp tests and boring blast radius.
  • The smell starts when the issue queue becomes the architecture process.
  • A branch is not evidence. The receipt is the task, context, commands, diffs, tests, and review notes.
  • Give agents sandboxes, narrow credentials, and explicit stop signs.
  • Do not reward volume unless you enjoy sorting confetti during an outage.

The smell

The borrowed hands smell appears when teams treat remote code work as capacity instead of change control. At first the jobs are safe: update a dependency, add a failing test, fix a typo in a docs page. Then the tickets get wider. Refactor the billing flow. Simplify authorization. Improve performance. Make the import pipeline more robust, a phrase that has ruined many afternoons.

The agent still returns a branch. The branch may even pass the tests. The problem is that the branch arrives from a narrow conversation with the repository, not from the messy social memory around it. It may not know that the odd duplicate function exists because one customer exports CSV with a medieval delimiter. It may not know that a slow query is kept slow because the fast path once melted a lock table. It may not know that the ugly interface is ugly because three teams share it and none of them answer calendar invites.

Humans miss these things too. That is not an excuse. It is a reminder that the system needs guardrails for everyone, especially for a worker that can produce plausible diffs without feeling the shame of pager duty.

Why it happens

Issue trackers make code work look more separable than it is. A ticket has a title, a description, a label, maybe a screenshot, and the comforting fiction of scope. A remote worker loves this format because it can turn the text into a plan. Managers love it because throughput becomes visible. Engineers love it for roughly ten minutes, until they review five branches that each solved the ticket and nicked a different pipe behind the wall.

The economic pressure is real. If a machine can clear small tasks, people want to feed it larger tasks. If it can open ten pull requests, someone will ask why it cannot open fifty. The metric creeps from saved time to generated activity. Soon the team is not asking whether the change should exist. It is asking whether the change is acceptable enough to merge before lunch.

Remote execution adds another layer of scent. The agent needs tools. It may need package registries, test databases, internal docs, issue comments, build logs, feature flags, and secrets that should not be secrets but have somehow become load-bearing folklore. Every permission turns the worker from a text editor into a participant in the production habitat. That deserves more ceremony than a happy checkbox called "allow repository access".

The pattern

Treat remote coding agents as constrained change producers. They may propose work. They may gather evidence. They may not become an unlabelled side door into design, security, or release authority.

Start by shaping the work. Good tasks have a small surface area, a clear failure, local reproduction steps, and tests that mean something. Bad tasks ask for judgment across product intent, data contracts, permissions, performance, and old promises made in conference rooms that no longer exist. If a senior engineer would need three conversations before editing code, do not throw the ticket into the hopper and call it modernization.

Require a receipt with every branch. The receipt should include the prompt or task text, repository state, files touched, commands run, test results, skipped tests, assumptions, and any places where the worker guessed. This is not a diary. It is the chain of custody for a change. Without it, reviewers have to reconstruct the little adventure from a diff and a brave commit message.

Build sandboxes that are boring on purpose. The worker should have short-lived credentials, scoped network access, disposable compute, and no path from curiosity to production data. If it needs a sample database, give it one. If it needs logs, scrub them. If it needs to run a migration, the answer is usually "write the migration and stop there". A tool that can edit code and touch real systems is no longer just helpful. It is holding a wrench near the gas line.

Make review narrower, not lazier. A reviewer should know what kind of change this is, which tests matter, which risk category applies, and which human owns the decision to merge. For tiny patches, that may be quick. For behavioral changes, require design notes or human pairing before code generation starts. The agent can draft, but it should not quietly decide that the architecture would look nicer if the service boundary moved four inches to the left.

Keep score by outcomes. Count rework, rollback rate, review time, escaped defects, test improvements, and the number of branches closed because the task was poorly framed. Pull request count is a vending machine metric. It tells you snacks came out. It does not tell you whether dinner is ruined.

The fart test

  • Can you say which tasks are safe for remote coding without arguing from optimism?
  • Does every branch include a useful receipt, not just a cheerful summary?
  • Are credentials short lived, scoped, and boring to audit?
  • Can reviewers see the commands, tests, assumptions, and skipped checks?
  • Is someone measuring rollback and rework instead of celebrating branch confetti?

If most answers are no, you do not have delegated development. You have a code piñata hanging over the merge queue. It may drop candy. It may also drop a billing regression wearing a party hat.

Use remote coding agents. They are useful, and refusing them on principle is just another way to make humans perform paste rituals in expensive chairs. But give the borrowed hands a workbench, a checklist, and a locked door behind them. The future of software may include machines opening pull requests. The future of architecture still depends on knowing which hands were allowed near the load-bearing beams.
