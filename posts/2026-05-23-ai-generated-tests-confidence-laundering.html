AI-generated tests and the smell of confidence laundering

Generated tests feel like free adulthood. The agent reads the code, writes a tidy suite, mocks half the universe, and presents a green checkmark with the calm of a notary stamping a haunted deed. Coverage goes up. The pull request looks responsible. Nobody has to admit the tests mostly prove that the current code continues being itself.

I like generated tests. I also like smoke alarms, seatbelts, and the little rubber duck that keeps an engineer from explaining OAuth to the coffee machine. Useful things become dangerous when we confuse their presence with their purpose.

A test suite is not proof that the system works. It is proof that somebody wrote down a belief and made the computer enforce it.

Short version

  • AI is good at producing test-shaped code. It is weaker at deciding what truth the test should protect.
  • The smell appears when generated tests raise coverage while copying the implementation's assumptions.
  • Good generated tests need human-owned oracles, named risks, and failure examples.
  • Measure whether tests catch wrong behavior, not whether they decorate the diff with green confetti.
  • If the test only proves that the mock returned what the mock was told to return, open a window.

The smell

The confidence laundering smell appears when a team uses AI to generate tests after the implementation exists, then treats the new green suite as evidence that the change is safe. The tests pass because the agent inferred the behavior from the code under test. The code says discounts stack. The test checks that discounts stack. Nobody asks whether discounts should stack, especially after midnight when the coverage badge is finally purring.

This is not fake work. The files are real. The assertions are real. The CI minutes are regrettably real. The problem is that weak tests can convert uncertainty into ceremony. Risk enters as a design question and exits as a spreadsheet cell labeled 87% coverage. That is laundering. Same smell, nicer shirt.

You see it in tests that assert implementation details instead of behavior. You see it in mocks that repeat the production call graph until the test becomes a dollhouse version of the bug. You see it in snapshots blessed on first run because nobody wants to read 700 lines of serialized component soup. You see it when a generated test says "should handle errors" and the error is a string the production system will never emit.

The nastiest version is the regression test that captures a bug as policy. The agent sees current output, writes an assertion, and the team merges it because the suite is now fuller. Two weeks later someone fixes the real behavior and the test fails, indignant as a tiny courthouse. Congratulations. You have appointed the bug to a lifetime seat.

Why it happens

AI test generation starts from available context. Most of the time, that context is the implementation, a few neighboring tests, and maybe a docstring written during a more innocent sprint. The model can infer patterns from those materials, but it cannot reliably recover the missing contract. If the contract is not written down, the agent often substitutes the code's current behavior. That is understandable. It is also how a mirror becomes a map.

Testing has two jobs that look similar from a distance. One job checks that code still does what we already believe it should do. The other job discovers whether our belief is wrong. Generated tests are comfortable with the first job because examples are cheap. The second job requires domain knowledge, adversarial imagination, and the nerve to ask why the API accepts a negative quantity in the first place.

Coverage metrics make the smell worse. Line coverage rewards execution, not skepticism. Branch coverage is better, but it still cannot tell whether the asserted outcome matters. A generated test can march through every line while gently avoiding the cliff. Management sees the number rise. Engineers see fewer red checks. The system sees nothing, because systems do not care how confident we feel while being incorrect.

There is also a workflow trap. Teams often ask the agent for tests at the end, when the shape of the solution already feels settled. At that point the prompt is usually "write tests for this file," not "attack this requirement until it squeals." The agent obliges. It writes tidy confirmation. Tidy confirmation is comforting. Comfort is not a quality strategy, though it does pair nicely with bad coffee.

The pattern

Use contract-first generation. Give the agent the requirement, invariants, examples, and failure modes before it sees the implementation. Ask it to propose cases from the contract, then compare those cases against the code. The order matters. If the implementation gets first speaking rights, the test suite tends to become its press secretary.

Name the oracle in every important test. An oracle is the thing that tells the test what correct means. It might be a business rule, a protocol spec, a public API contract, a security invariant, or a historical incident. Put that reason near the assertion. "Premium discounts do not stack because finance reconciles one promotion per order" is better than "expects total to equal 42.50." The first protects a rule. The second protects a number wearing a fake mustache.

Use AI for breadth, then make humans own depth. Let the agent draft boundary cases, boring permutations, parser oddities, and regression scaffolds. Then have a human select the risks worth protecting. This is the part we keep trying to automate away because it is uncomfortable. Too bad. Deciding what failure would hurt is architecture, not clerical work.

Run mutation testing or deliberate sabotage when it matters. Break the implementation in small plausible ways and see whether the generated suite notices. Flip a comparison. Remove an authorization check. Change rounding. Delete a retry. If the tests still pass, they are not tests yet. They are decorative seat cushions in the incident bus.

Keep generated tests readable. A test that nobody understands will become landfill with assertions. Prefer small examples with direct inputs and visible outcomes. Avoid mock cathedrals unless the system boundary truly requires them. If the setup is larger than the behavior being protected, the test may be modeling your architecture smell instead of catching it.

The Fart Test

  • Can you point to the requirement or incident this test protects?
  • Would the test fail if the implementation made a plausible business or security mistake?
  • Does the assertion check behavior, or does it repeat the code's internal choreography?
  • Could a new teammate read the test and understand why the outcome matters?
  • If you delete the mock setup, does anything meaningful remain?

Generated tests are a useful draft, not a priesthood. Let the machine write the first pass. Make a human decide what truth deserves guarding. Otherwise the suite will be green, the badge will be shiny, and the room will smell like certainty left too long in a sealed container.
