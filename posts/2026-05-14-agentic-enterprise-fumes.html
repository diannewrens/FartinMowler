Agentic Enterprise Fumes

We have reached the familiar phase of a new software movement where every vendor deck contains the same three boxes: a model, a tool, and an arrow labeled “reasoning.”

There is something real here. Giving software systems a controlled way to perceive context, choose tools, and iterate toward an outcome is a meaningful shift. It changes how we design boundaries. It changes how we test. It absolutely changes how we assign blame when the quarterly forecast deck contains a recipe for soup.

Not every agent is an architecture. Sometimes it is a cron job wearing a little hat.

The useful question is not “Should we use agents?” The useful question is “Where does autonomy create leverage, and where does it merely move uncertainty into a more expensive runtime?”

Early smells

  • Prompt soup: business logic hidden in a blob of prose nobody reviews.
  • Tool confetti: exposing every internal API because the demo looked magical.
  • Optimistic memory: storing everything forever, then acting surprised when the agent remembers nonsense with confidence.
  • Accountability vapor: no durable trace of why the system did what it did.

A better starting pattern

Treat the agent as an orchestration boundary, not a wizard. Give it narrow tools, explicit state, observable runs, and boring rollback paths. The more magical the interface feels, the more mundane the operating model must be.

In other words: enjoy the paradigm shift, but open a window.
