Structured outputs and the smell of schema-shaped lies

Structured output is one of the better things to happen to LLM application architecture. Asking a model for JSON that matches a schema is cleaner than begging it to format an answer politely and then scraping its prose like a raccoon with a regex.

The smell starts when teams treat valid JSON as verified truth. The response has the right keys. The enum is legal. The dates parse. The confidence field says 0.91, which feels official in the same way a laminated badge feels official on a man walking toward the server room with bolt cutters.

A schema can tell you the fart has a container. It cannot tell you whether the fart is evidence.

Short version

  • Structured outputs are useful because they turn model responses into data your system can validate, route, store, and test.
  • They get dangerous when shape validation replaces truth validation, policy checks, and provenance.
  • The fix is to separate syntax, semantics, source evidence, and business authority. Each needs its own gate.
  • If your pipeline says "valid" when the model invented the premise, you built a very tidy lie dispenser.

The smell

You see it first in the happy path. A support classifier returns {"intent":"refund_request","urgency":"high","eligible":true}. The downstream workflow opens a refund task. A dashboard increments a metric. Everyone admires the lack of string parsing. Somewhere, a customer gets routed into a process based on a fact the model inferred from vibes, a partial transcript, and the universal human desire to make the demo move along.

The bug report is annoying because nothing is technically broken. The JSON is valid. The schema passed. The enum value exists. The workflow did what it was told. The logs are neat enough to frame. The problem is that the model answered a question it was not authorized to answer. It converted text into a business decision, and the schema gave that decision a little blue blazer.

This is schema-shaped lying. The system did not hallucinate in paragraph form, so it feels safer. It hallucinated in a format your code trusted more. That is worse. Humans are suspicious of a rambling answer. Systems are obedient to fields.

Why it happens

Developers like structured outputs because they make LLMs feel less like weather. You define a schema. The model returns an object. The application stops arguing with Markdown. This is a real improvement. Without it, every integration becomes an archaeological dig through bullet points, apology sentences, and surprise preambles.

But a schema is mostly a syntax contract. It says the value must be a number, a string, an enum, an array, or an object with certain required fields. It can reject "banana" where the workflow expects "low", "medium", or "high". It cannot decide whether "high" is justified. It cannot know whether the model saw the latest policy. It cannot know whether the transcript had enough evidence. It cannot know whether the answer should have been "I do not know," unless you make that a first class outcome and reward the system for choosing it.

The second trap is repair. Many structured-output pipelines add a retry loop: if the model returns invalid JSON, ask it to fix the JSON. That is fine for a missing comma. It is suspicious for missing evidence. Repair loops can launder uncertainty into compliance. The model fails to produce a valid answer, gets nudged, and eventually emits something that fits. The system records success. The truth quietly leaves through the bathroom window.

The third trap is overloading one object with too many meanings. Teams ask for extraction, classification, policy judgment, explanation, routing, and confidence in one response. The object looks convenient, but its fields have different authority levels. "Customer mentioned refund" is an extraction. "Customer is eligible" is a policy decision. "Refund now" is an action. Putting them next to each other in JSON does not make them equally safe.

The pattern

Split the gates. Validate syntax first, because malformed data should not enter the system. Then validate semantics: do the values make sense together, are required citations present, are timestamps plausible, does the answer include an abstention when evidence is missing? Then validate authority: is this model allowed to decide this field, or may it only propose a value for a human, rule engine, or service to confirm?

Make provenance boring and mandatory. Any extracted fact should point back to source text, document IDs, tool calls, database rows, or user inputs. If the model says a customer asked for cancellation, store the span or message that supports it. If it classifies a security alert, store the signals it used. A field without provenance should be treated like a sandwich found on a bus: maybe fine, not production evidence.

Separate observations from decisions. Let the model produce observed_intent, supporting_quotes, and missing_information. Let deterministic code, policy services, or human review decide eligible, approved_amount, and next_action. This adds plumbing. Good. Plumbing is what keeps smells from becoming atmosphere.

Design for abstention. Include explicit values like unknown, insufficient_evidence, and needs_review. Do not treat them as failures to be retried into prettier answers. Track them as normal outcomes. A model that can say "I cannot tell" is less exciting in a demo and much less likely to quietly chew through your edge cases like a goat in a paperwork factory.

Test the contract with adversarial fixtures. Feed the pipeline ambiguous transcripts, stale policies, contradictory documents, prompt injection attempts, and examples where the right answer is no answer. Your tests should verify not only that the JSON parses, but that the system refuses to promote unsupported fields. The point is not to make the model honest. The point is to make dishonesty unable to travel first class.

The Fart Test

  • Does every business decision field have a separate authority check outside the model response?
  • Can each extracted fact point to source evidence, not just a confidence score?
  • Does the schema include abstention states, and does the workflow respect them?
  • Do retry loops fix formatting without inventing missing evidence?
  • Can tests prove the system rejects a well-formed object with unsupported claims?

Structured outputs are good architecture hygiene. Use them. Just remember that a schema is a jar, not a judge. Label the jar, sniff the contents, and do not let valid JSON march into production wearing truth's little hat.
