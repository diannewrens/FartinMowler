The Model Context Protocol Catalog

March 2026. The industry has discovered, with the startled expression of a man finding a raccoon in his HVAC system, that language models are more useful when connected to the rest of the computer. This insight has been rediscovered every quarter since 2022 under names such as tools, functions, agents, plugins, actions, assistants, and the thing Gary wrote that can restart Kubernetes if you phrase the request politely.

The Model Context Protocol, or MCP, is the latest attempt to stop every integration from becoming a custom tube taped to the side of a chatbot. This is good. Protocols are civilization. They let two pieces of software disappoint each other in predictable formats.

MCP gives us a vocabulary for exposing tools, resources, and prompts to model clients without rebuilding the entire buffet for each host application. It does not, however, remove architecture. If anything, it concentrates architecture into a smaller room, warms it gently, and asks whether anyone remembered ventilation.

1. The adapter smell

The first MCP server in any organization is usually an adapter around an API that already exists. This is proper. The second is also an adapter. The ninth is an adapter around three adapters, two shell scripts, and a Slack bot from 2019. At that point the faint odor is not innovation. It is coupling.

An MCP server should translate model-friendly operations into bounded system actions. It should not become the new enterprise service bus simply because it speaks JSON and the LLM says thank you.

  • Good adapter: create_linear_issue with explicit fields, validation, and project constraints.
  • Risky adapter: linear_graphql where arbitrary queries are accepted from model text.
  • Bad adapter: do_business_thing, which forwards natural language to a privileged backend and hopes the vibes pass QA.

2. The tool pantry

MCP makes tools discoverable. Discovery is intoxicating. Soon every client starts with eighty-seven tools: filesystem, calendar, GitHub, Datadog, Jira, browser, payments, Snowflake, warehouse forklift, and a small weather service added by an intern because the demo needed context.

The tool pantry pattern says tools should be present, labeled, and reachable, but not all placed on the counter. Organize them by task context. A coding assistant needs repository tools, issue tools, and maybe CI logs. It probably does not need invoice refunds.

If a tool is available "just in case," the case will eventually arrive wearing a fake mustache and carrying user input.

3. The least-tool principle

The least-tool principle is least privilege wearing a little paper hat that says latency. Give the model the minimum tool surface required to complete the current job. This sounds obvious until the first executive demo, when someone asks whether the assistant can "just also update Salesforce," and suddenly the recipe bot can modify pipeline forecasts.

Implement least-tool in layers. At startup, register servers broadly. At session creation, select role-appropriate servers. At task planning, pass only the operations relevant to the current step. At execution, require confirmation or policy approval for destructive actions.

4. The resource boundary

MCP resources are often described as context the model can read. That is accurate in the way "the ocean is wet" is accurate: technically true, architecturally insufficient. Resources decide what becomes context, when it is loaded, how fresh it is, and whether the model sees one document or the entire attic.

  • Use stable resource identifiers, not fragile file paths embedded in prose.
  • Return metadata first: title, owner, freshness, permissions, size, and summary.
  • Chunk large resources intentionally, preserving headings and citations.
  • Make stale data visible. "Last indexed six weeks ago" is context too.

5. Prompt libraries, not prompt landfills

MCP prompts are reusable interaction templates. This is useful because every organization eventually develops a folklore of prompts: the incident review prompt, the PR summary prompt, the "make this sound less like legal wrote it after coffee" prompt. Without structure, these live in Notion pages, Slack pins, and the private notes of the one engineer who still says prompt engineering without irony.

A prompt library should encode tasks, inputs, constraints, and expected outputs. It should not become a landfill of inspirational spellcraft. "You are a world-class ninja rockstar strategist" is not a reusable asset. It is confetti in a config file.

6. Local servers and the warm sock drawer

Local MCP servers are charming. They run over stdio, live near the user, and can touch files, shells, editors, and devices. They feel like Unix pipes with a language model wearing mittens. For developer workflows, local servers are often the right answer.

But local does not mean safe. It means close. A local server with filesystem access can do local damage. A local server that inherits the full environment can exhale credentials like a nervous trumpet. The pattern is capability hygiene: pass only required directories, filter environment variables, pin package versions for serious work, and log tool calls locally.

7. Remote servers and the enterprise fog machine

Remote MCP servers are inevitable. Teams want shared integrations, centralized auth, policy enforcement, usage logs, and one place to update the Salesforce wrapper after Salesforce changes the API for spiritual reasons. A remote server can be excellent architecture: easier to govern, easier to observe, easier to patch.

It can also become fog. Once the tool catalog lives behind a remote endpoint, clients may stop understanding what actions really occur. "Call the customer server" might read records, compute entitlements, modify subscriptions, and alert an account manager. The model sees one tool. The audit team sees a scented cloud.

8. Authentication is not a mood

Many early tool systems authenticated by vibes. The user was logged into the chat client, the tool had a token somewhere, and the model was assumed to be acting on behalf of whoever typed last. This works until a shared channel, copied transcript, scheduled agent, or malicious document asks the assistant to rotate the payroll account.

MCP systems need explicit identity propagation. Who is the human? What workspace are they in? What server accepted the request? Which downstream credential was used? Was the action delegated, automated, or directly confirmed? These are not bureaucratic questions. They are the difference between an assistant and a raccoon with OAuth.

9. Audit as a first-class output

Tool calls are decisions with side effects. Even read calls matter, because reading can expose confidential context that shapes subsequent output. An MCP architecture without audit is a restaurant that keeps receipts only for fires.

Good audit records the actor, tool name, arguments after redaction, authorization decision, resource touched, result class, duration, and correlation IDs. For destructive operations, store the approval event and the precondition checked.

10. The catalog is a product

The word catalog invites negligence. A catalog sounds like a generated list, something the system emits after scanning servers. But the MCP catalog is a product surface. It is how the model understands your organization's capabilities. Bad names, overlapping tools, stale descriptions, and inconsistent schemas create behavior that looks like model stupidity but is often catalog mildew.

Curate the catalog. Remove dead tools. Merge duplicates. Mark dangerous tools. Write examples. Keep schemas strict. Test descriptions by asking a model to choose among similar tools and explain its choice.

11. Error messages for models and mammals

Traditional APIs return errors for programmers. MCP tools return errors into a reasoning loop. That means error messages are not just diagnostics; they are steering inputs. "500 internal error" tells the model nothing except perhaps to try again until rate limits squeal.

Design errors with recovery paths. Indicate whether the failure is permanent, transient, authorization-related, validation-related, or ambiguous. Include safe next steps. A system is reliable when it fails in ways that make the next correct action obvious.

Closing the vent

MCP is not the final protocol. No protocol is final unless it is printed on a mainframe manual and guarded by someone named Don. But MCP captures a shape the industry needed: a common way for models to discover and use external capabilities without every application becoming a bespoke drawer of knives.

The winning teams will not be the ones with the longest tool lists. They will be the ones with the cleanest boundaries, the dullest auth, the best audit, and the fewest mysterious adapters emitting warm architectural gas behind the drywall.
